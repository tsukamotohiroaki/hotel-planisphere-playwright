# テスト計画

## 目的
HOTEL PLANISPHEREの主要機能（下記「テストする範囲」）が期待どおり動くことを確認し、回帰テストを自動化する。
あわせて、何を自動化し、何を手動に残すかを判断する。

### 期待結果の根拠（テストベース）
仕様書は存在しないため、以下を期待結果の根拠とする。
1. 現行サイトの画面・振る舞い
2. 公式e2eテスト（作者が「正しい」とした動き。1と食い違う場合は、1を正とする）
3. 作者リポジトリのREADME（利用ルール・前提）
4. ソースコード（料金計算などのルールの裏取り）

仕様の把握はテスト分析で行い、テスト設計で期待結果を具体的な値にする。
期待結果ごとに根拠（1〜4）を記録する。

## 範囲

### テストする範囲
- ログイン
- ログアウト
- 会員登録
- マイページ（ログインしたアカウント名の表示）
- 会員ごとの宿泊プラン一覧の表示
- 宿泊料金の計算（平日・休日、宿泊数、人数、追加プランによって合計金額が正しく表示されること）
- 宿泊予約
- 予約確認
- 退会

### テストしない範囲
| 対象外 | 理由 |
|---|---|
| 非機能（性能・負荷） | Playwrightは負荷テスト向きではなく、READMEの利用規約で負荷テストが禁止されているため |
| 操作感 | 主観的な評価であり、自動テストでは判定しにくいため |
| Chromium以外のブラウザ | READMEに「Google Chromeで動作確認した」とあるため、Chromiumを基準とする |
| 日本語以外の言語 | 英語版もあるが、画面のロジックは共通と想定し、日本語版を優先する |

※ `playwright.config.ts` の `projects` を Chromium のみに揃える

## 方針（アプローチ）
- テスト技法はJSTQBの用語を使う
  - 同値分割
  - 境界値分析
  - デシジョンテーブル
  - 状態遷移
- テストケースの漏れと重複を防ぐために MECE を使う
- 優先度は「不具合が起きた時のユーザーへの影響度」と「不具合の起きやすさ」の2つの軸で決める
- 1機能ずつ「分析→設計→自動化→CIで回す」を1周し、段階的に範囲を広げる
- 各工程の成果物はレビューを受け、指摘への対応方針（反映する／理由をつけて見送る）を決めてから書き直す

## 役割
自分は分析・設計・実装を担当し、AIはレビューとGit・CI作業を担当する。

## リスク
| リスク | 対策 |
|---|---|
| 時間が確保できない | 1日最低4時間を確保する |
| 細部に拘りすぎる | 1日の初めにノルマを設定する。1時間ごとに進捗をAIに共有し、順調か客観的に判断してもらう。レビュー時間を先に決め、時間になったら途中でも見せる |
| テスト対象サイトのドメイン変更 | URLを `baseURL` に集約し、修正を1か所で済ませる。CIが赤になることで気づく |
| テスト対象サイトの停止 | READMEの手順でサイトをローカルに立ち上げ、`baseURL` を切り替えて回す。CIが全て赤になったら、まずサイトにアクセスできるか確認する |
| テスト対象サイトの仕様変更 | 期待結果の根拠を設計書に残し、失敗時に「不具合」か「仕様変更」かを切り分ける。作者リポジトリの更新をWatchする |
| テストデータの干渉 | データはブラウザ側に保存されサーバーで共有されないため影響は小さい。テストごとに新しいブラウザで実行する |
