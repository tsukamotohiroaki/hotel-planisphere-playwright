# テスト分析 レビュー（第2回）

- 日付：2026-10-30
- 対象：[docs/test-analysis.md](../test-analysis.md)（第2版）
- レビュアー：Claude（ベテランQAエンジニアの立場で助言）

## 全体
第1回から大きく良くなった。特に良い点は次の3つ。

- 「画面 → 機能」に分けて、メニューに出てこない機能（宿泊料金の計算、アイコン設定）まで見つけている。宿泊料金の計算が2つの画面にまたがることにも気づけている。
- 根拠を自分で確かめている。料金のルールはソースコードで気づいたあとサイトで確かめ直し、予約フォームの初期値は自分で登録した値で確かめている。テストベースの優先順位を、自分の手で守れている。
- 期待どおりかどうかを、自分で判断している。ログアウト後の「戻る」、重複メールのメッセージ、性別「回答しない」→「未登録」について、気になる点を書き残し、判断の理由をつけている。

## 1. 画面 → 機能
- 「テストしない範囲」は画面の名前ではなく、分類になっている。アイコン設定には自分の画面（icon.html）がある。一覧の形をそろえるとしたら、どう書くか？

## 2. 機能ごとの分析
- 「目的」の行があるのは9機能のうち6つ。ログイン・会員登録・マイページには目的がない。ログインの目的は10/28にチャットで答えている。目的は優先度の影響度を決めるときの手がかりになった。3つにも書くか？
- 宿泊料金の計算で、観光（お得な観光）を2泊にした組み合わせは、まだサイトで確かめていない。「早期チェックインと観光：1,000円 × 人数」のうち、観光の部分の根拠はどれになるか？
- 料金のメモでは、同じ追加プランが「昼からチェックイン」（観察）と「早期チェックイン」（ルール）の2つの名前で出てくる。テスト設計では、どちらの名前を使うか？
- 退会の「定義済みユーザーは『退会する』が押せない」は、「異常系（退会後）」の下にある。これは退会した後の話か？

## 3. 優先度
- 影響度と起きやすさの2つから、優先度をどう決めるか（組み合わせのルール）が書かれていない。たとえば「影響度：高・起きやすさ：低」と「影響度：中・起きやすさ：中」では、どちらを先にするか？
- 予約確認の起きやすさを「低（入力内容を表示するだけ）」としている。でも、合計金額はこの画面に表示される。宿泊料金の計算と予約確認の関係を、どう整理するか？

## 4. 見つけた気になる点の扱い
- ログアウト後の「戻る」でマイページが見える件と、会員登録で登録済みのメールアドレスが分かってしまう件。どちらも分析に書き残せている。この2つは、このあと何として扱うか（不具合として報告する／仕様として受け入れる／範囲外として見送る）？

## 5. 第1回の指摘の行方
- 第1回の「3. 自動化の基準」（なぜ自動化するか）は、第2版では扱っていない。どの Issue で決めるか？
