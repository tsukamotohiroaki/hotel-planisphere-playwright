# テスト設計 レビュー（第1回）

- 日付：2026-10-30
- 対象：[docs/test-design.md](../test-design.md)（初版・途中。追加プランのデシジョンテーブルは未着手）
- レビュアー：Claude（ベテランQAエンジニアの立場で助言）

## 全体
初めてのテスト設計としては、とても良い。特に良い点は次の3つ。

- 技法を自分で足している：宿泊数と人数に、聞かれる前に境界値分析を足した。曜日にも「平日→土日」「土日→平日」の2つの境目を見つけ、境界値分析を当てはめている。
- 重複を ID でまとめている：宿泊数-02・人数-02・人数-06 を「〜と同じ」とし、1つのテストケースが複数の役割を兼ねることを表に残している。MECE の「重複」を自分で見つけられた。
- 期待結果が合わないとき、まず自分の入力を疑えた：9泊の金額が合わなかったとき、宿泊日が日曜になっていたことに自分で気づいた。

## 1. 条件と同値クラス
- 宿泊数と人数の同値クラスの表は、素泊まりだけになっている。カップル限定プランの範囲（宿泊数 1〜2泊、人数 2人）は、どこで分かるか？
- 曜日の「平日」に「祝日も含む」と書いている。でも、祝日のテストケースはない。祝日の扱いは、実際のホテル予約サイトでも間違いが起きやすいところ。テストケースにするか？

## 2. 技法の選定理由
- 境界①の例は「カップル限定・2名 → 36,000円」だが、テストケースの曜日-03 は「素泊まり・1人 → 12,375円」になっている。どちらを正とするか？
- Issue #6 で挙げた技法は4つ（同値分割・境界値分析・デシジョンテーブル・状態遷移）。状態遷移を使わない理由は書かれているか？

## 3. テストケース
- 宿泊数と人数の「範囲外」のケース（0泊・10泊・0人・3人など）は、エラーメッセージを確かめている。これは「宿泊料金の計算」のテストか、「宿泊予約」（入力ルール）のテストか？分析のレビューの 3-2 で、予約確認と料金計算の仕事を切り分けたことを思い出す。
- 期待結果の金額は、どの画面のどこで確かめるか？（宿泊予約画面の「合計」か、宿泊予約確認画面の「合計 ◯円（税込み）」か）
- 「月曜から」の月曜は、いつの月曜か？宿泊日は「当日〜3か月先」しか選べない。テストを実行する日によって、選べる日は変わる。
