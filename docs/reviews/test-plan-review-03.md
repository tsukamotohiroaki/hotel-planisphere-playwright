# テスト計画 レビュー（第3回）

- 日付：2026-10-27
- 対象：[docs/test-plan.md](../test-plan.md)（第2版）
- レビュアー：Claude（ベテランQAエンジニアの立場で助言）

## 全体
初版から大きく良くなった。特に良い点は次の3つ。

- テストベース（期待結果の根拠）：仕様書が無いことに自分で気づき、根拠に優先順位をつけ、期待結果ごとに根拠を記録すると決めている。面接で十分に話せる内容。
- リスクと対策の表：自分でコントロールできないリスク（サイトの停止、ドメイン変更、仕様変更）まで洗い出し、対策と「どうやって気づくか」まで書けている。
- 調べた事実が根拠になっている：作者の README を読み、「負荷テスト禁止」「データはブラウザ側に保存される」を根拠に使っている（レビュアーも作者リポジトリの README で記載を確認済み）。

## 1. テストベース
- 1（公式 e2e テスト）を最優先にした理由は何か？「e2e テストの期待値」と「サイトの今の動き」が食い違ったとき、どちらを正しいとするか？
- 4（ソースコード）から期待結果を作ると何が起きるか？ソースコードにバグがあった場合を考える。

## 2. 範囲
- 「進め方（1機能ずつ1周する）」が範囲の中にある。これは「何をテストするか」か、「どうやって進めるか」か？
- Chromium 以外を外す理由について、作者の README の該当箇所を一字一句読み直す。動作確認されたのは「サイト」か、別のものか？サイト側の事情とは別に、自分側の理由（時間やコストなど）はないか？
- 作者の README の「Site Structure」に、範囲に関わる記述がもう一つある（画面の大きさについて）。
- 「`playwright.config.ts` を Chromium のみに揃える」は計画で決めた作業。どの Issue で、いつやるか？

## 3. 方針
- CLAUDE.md の「docs の書き方」には、技法のほかにもう1つ、テストの作り方に関する決めごとがある。
- 優先度の軸が「影響度」だけになっている。Issue #5 には、もう1つの軸が書いてある。
- 「レビューを受けて書き直す」進め方も、方針の一部と言えないか？

## 4. スケジュール
- テスト分析が 10/28 の1日になっている。範囲の9機能すべてを洗い出して優先度をつけるのに、1日で足りるか？（足りると判断した理由があれば十分）

## 5. 完了基準
- 「段階的に範囲を広げる」一方で、完了基準は1つ。1周目の完了とプロジェクト全体の完了は同じか？

## 6. リスク
- 「1日最低4時間を確保する」は対策か、目標か？確保できなかった日はどうするか？
- 前回のプロジェクトで経験した失敗は、このプロジェクトのリスクにならないか？
